# TypeScript test fixture static-type agreement audit

## Executive summary

The issue is **meaningful test-maintenance debt and a limited confidence concern**, not evidence of a production schema defect. A non-mutating check of every TypeScript test file reports **40 diagnostics in 13 files**. **34 diagnostics in 10 files** concern domain fixtures or test calls to domain APIs; the other six are component harness and localization-test typing. Most errors come from five recurring families: current outpost/network objects, history action labels, cargo shapes, validation issues, and historical import objects typed as current objects. The count is diagnostic sites, not 40 independent causes.

The correction is a **medium parcel**: approximately 10 domain-test files, or 13 test files if the adjacent component/localization errors are included, plus a deliberate test type-check configuration/script after the fixtures are clean. No production-code change appears necessary. A few current-state tests are materially misleading about valid runtime shape, especially outposts without `explicitResourcePresence` and validation issues without `messageKey`. Historical malformed inputs are intentional and should remain so. This is suitable as the first parcel of the next sprint if the parcel explicitly includes a test-specific type-check gate and preserves migration tests.

## Current TypeScript and test compilation model

- `tsconfig.json` references `tsconfig.app.json` and `tsconfig.node.json`. The app project includes only `src`; the node project includes only `vite.config.ts`. `npm run build` invokes `tsc -b`, so a passing production build does not check tests.
- `tests/tsconfig.json` has `"noCheck": true` and `"include": ["./**/*.ts"]`. Even invoking this project as-is does not perform semantic checking, and its include pattern omits `.tsx` component tests. Overriding `noCheck` exposes 35 diagnostics in `.ts` files; including `.tsx` raises this to 40.
- `npm test` uses Node's `--experimental-strip-types` on `tests/*.test.ts`. It strips types and runs JavaScript without semantic TypeScript checking. `npm run test:components` uses Vitest/Vite transformation for five `.tsx` test files, also without a test type-check gate. `vitest.config.ts` explicitly includes `tests/**/*.test.tsx`.
- The existing `docs/BACKLOG.md` entry at “Bring the TypeScript test fixtures back into static type agreement” correctly notes excluded tests, missing character/outpost fields, older cargo shapes and module-resolution noise. This audit uses Bundler resolution, matching `tests/tsconfig.json`, so the inventory below is not inflated by NodeNext extension complaints.

## How drift is bypassed

The main bypass is **configuration and transpilation**, rather than widespread `any` or broad domain casts. Current fixtures are checked only against the call sites they happen to exercise at runtime. Runtime code often reads only selected fields; for example, availability checks do not need every persisted outpost field, and validation navigation does not need a display message key.

Four `Partial<Outpost>` override helpers appear in `itemSearchResults`, `manufacturingAvailability`, `stateLegibility`, and `validationDiagnostics`. The first three omit `explicitResourcePresence` from their base object, so the helper's declared `Outpost` result is false; the fourth supplies it correctly. Object spreading permits extra fields to flow through in other cases, while fresh nested literals still expose some excess-property errors. `Object.assign`, `Reflect.deleteProperty`, `structuredClone`, and `JSON.parse` are used to make historical or malformed import payloads. Those are legitimate at an untrusted-data boundary, but leave a typed variable claiming to remain a current `OutpostNetwork` after its required properties are deleted. The `as unknown as EventTarget` casts in keyboard/validation interaction tests and the partial `ReferenceData` cast in a reference-startup failure test are targeted DOM/failure simulations, not the cause of the domain fixture drift. No meaningful domain-fixture `as any`, duplicated production interface, or `satisfies` pattern was found in `tests/`.

## Impossible versus intentional invalid states

- **Stale and potentially misleading current objects:** current-schema (`schemaVersion: 4`) outpost builders in the five current-shape sites above omit required `explicitResourcePresence`. `createDefaultOutpost` supplies this field, and current external import validation requires it. The tests pass because their exercised code paths tolerate or never inspect the omission. This does not prove the full current-schema state is valid.
- **Stale and misleading test-only metadata:** `validationInteraction` issues use `message` without `messageKey`; production validation issues require a localization key. The interaction functions being tested do not consume the message, so the navigation/identity assertions can pass while using an issue shape that production rules cannot produce. The `character` category in `validationDiagnostics` is outside the `ValidationCategory` union; production skill validation uses an allowed category. The extra `CargoLink.type` field is stale but harmless for the particular inbound-availability assertion because endpoint data drives that behavior.
- **Intentional historical input:** `resourcePersistenceCompatibility.test.ts` begins with schema 3, so absence of `capabilities` and `explicitResourcePresence` is part of what migration must add. `networkLifecycle.test.ts` deliberately mutates schema-1/2/3 payloads and tests pad-local links and malformed import rejection. These inputs are not valid current domain objects, but they are valid test subjects at the migration/import boundary. The issue is typing them as current objects while constructing or mutating them.
- **Intentional malformed or partial simulations:** `JSON.parse`/`Object.assign` payloads in storage and import tests, DOM `EventTarget` stubs, and the intentionally incomplete `ReferenceData` used to test startup failure should remain explicit boundary/failure fixtures. Their invalidity should not be “fixed” into valid current-domain data.
- **Other runtime invariants:** the compiler inventory does not establish that every type-correct fixture is a valid reachable gameplay state. For example, some reference IDs are synthetic and some tests purposely exercise warnings. No additional production schema contradiction was demonstrated by this audit.

## Scope estimate and recommended correction strategy

Classify as **medium**. The work is localized to roughly 10 domain-test files for the 34 core diagnostics, or 13 files including the six adjacent component/localization diagnostics. A separate test-specific configuration/script change is appropriate after the tests check cleanly. This is not a broad factory or framework redesign. Some edits are mechanical, but history descriptors and historical-payload typing require care so assertions keep their intended meaning. Expect modest history-label expectation churn; no snapshot files were identified as requiring regeneration.

Recommended implementation order:

1. Add a non-emitting, checking test project or command that includes both `.ts` and `.tsx` and uses Bundler resolution. Keep it separate from the production `tsc -b` scope until green, then put it in routine verification/CI. Do not rely on the existing `noCheck` test project as a gate.
2. Correct valid-domain defaults in the three incomplete `Partial<Outpost>` builders and the two direct outpost literals. Keep local builders where test intent is clearer; only share a minimal current-outpost factory if duplication still causes drift. Use `satisfies Outpost`/`OutpostNetwork` for representative literals or explicitly typed builder returns to catch future missing/excess fields.
3. Update history actions to `HistoryLabelDescriptor`, preferably through a small local descriptor helper for repeated test labels. Review expected history presentation rather than casting strings.
4. Fix current cargo and validation fixtures, and component harness contracts. Broaden the planned-supply state to `CargoItem[]`; update the removed session argument; supply explicit reference data to `App` tests. Resolve the narrow localization test inference without broad casts.
5. Isolate schema-1/2/3 and intentionally malformed import payloads as raw/unknown or accurately typed historical-input values before deserialization. Avoid asserting that pre-migration payloads satisfy the current `OutpostNetwork`. Preserve all existing migration/rejection cases.
6. Run the dedicated test type-check, Node suite, component suite, production build, and diff checks before enabling the new gate.

Production-code changes are **not currently indicated**. If a corrected valid fixture changes a behavior assertion, investigate that specific discrepancy before changing production semantics. Do not weaken `Outpost`, `Character`, `ValidationIssue`, or action types to accommodate stale tests.

## Risk assessment

- **Product risk: low to moderate.** Current-state tests with omitted fields can hide a failure in code paths that read them. The `App` harness does not provide required reference data, so those storage tests do not exercise the full production wiring. No observed test/build failure or concrete production schema defect follows from the audit.
- **Test-maintenance risk: moderate.** A semantic-check bypass plus several duplicated local builders allowed schema/API changes to leave tests behind. Without a gate, this can recur.
- **Refactor risk: moderate but bounded.** Tightening the test project surfaces many diagnostic sites at once, mostly from repeated history labels. Historical malformed-input tests need a boundary representation to avoid losing coverage. Broadly converting every fixture or changing production types would raise risk unnecessarily.

## Commands and reproduction notes

Inspection used `git status`, `git branch --show-current`, `rg` searches over `tests/`, `src/`, and `docs/`, and reads of TypeScript/Vitest configuration, canonical models, defaults, migration, import validation, history/validation contracts, representative tests, and the backlog entry. The branch was `staging`. Before the audit, the only working-tree item was the untracked supplied brief in `docs/implementation-briefs/`.

TypeScript 6's direct-file invocation requires `--ignoreConfig` when a `tsconfig.json` is present. The following PowerShell command checked all 33 TypeScript files under `tests/` without creating a configuration file or emitting code:

```powershell
$testFiles = @(Get-ChildItem -LiteralPath tests -Recurse -File | Where-Object { $_.Extension -eq '.ts' -or $_.Extension -eq '.tsx' } | ForEach-Object FullName)
& .\node_modules\.bin\tsc.cmd --ignoreConfig --noEmit --target ES2023 --lib ES2023,DOM --module ESNext --moduleResolution Bundler --types node,vite/client --allowImportingTsExtensions --verbatimModuleSyntax --moduleDetection force --jsx react-jsx --skipLibCheck --pretty false $testFiles
```

Result: **40 compiler diagnostics / 13 test files**. A narrower `tsc -p tests/tsconfig.json --noCheck false --noEmit --pretty false` check reported **35 diagnostics** because that project excludes `.tsx`. Invoking the test project without overriding `noCheck` is not a semantic test. The first attempt at a direct-file invocation was rejected by TS5112 until `--ignoreConfig` was supplied; it produced no fixture inventory.

Validation: `npm test` **183/183 passed**; `npm run test:components` **52/52 passed**; `npm run build` **passed** (with Vite's existing large-chunk advisory). The audit deliberately did not run benchmarks or change fixtures/configuration.

## Limits of the audit

This is a static inventory and representative source review, not exhaustive proof that every test fixture describes a reachable game state. Diagnostic counts may shift after the first helper is corrected. The direct-file experiment uses the same principal compiler options as `tests/tsconfig.json` but bypasses its `noCheck` and expands the file set to `.tsx`; a future permanent test project may reveal slightly different diagnostics under stricter options. Independent gameplay questions listed in the supplied brief were not investigated. The only intended repository edit is this report; no implementation, test, configuration, dependency, or lockfile change is part of this audit.
